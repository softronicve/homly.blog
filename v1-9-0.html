v1.9.0: el bug que no se ve

26 de julio de 2026

Seis características nuevas, pero la que más importa arregla algo que nunca ibas a ver reportado: una búsqueda que devuelve el resultado equivocado, una de cada veinte veces.

La carrera

Escribes casa en un buscador. Se dispara la petición. Antes de que vuelva, escribes casaquinta. Se dispara la segunda. La segunda responde rápido, se pintan los resultados de casaquinta… y medio segundo después aterriza la primera y sobrescribe la lista con los resultados de casa.

El campo de búsqueda dice casaquinta. La lista muestra otra cosa. Nadie reporta este bug porque nadie sabe describirlo: aparece cuando la red tiene un hipo, se arregla solo al escribir una letra más, y no se reproduce cuando vas a revisarlo. Si escribes el fetch a mano en onMount, lo tienes.

store.resource lo hace imposible:

store.resource('propiedades', ['q'], (q, { signal }) =>
  fetch(`/api/propiedades?q=${encodeURIComponent(q)}`, { signal })
    .then(r => {
      if (!r.ok) throw new Error(`HTTP ${r.status}`);
      return r.json();
    }),
  { debounce: 300 },
);

Cada ejecución aborta la anterior y lleva un token. Cuando una respuesta vuelve, si su token ya no es el vigente, se descarta sin tocar nada. La vieja no puede ganarle a la nueva ni aunque llegue después.

Tres claves, cero directivas nuevas

resource no devuelve un objeto: registra tres claves en el store —propiedades, propiedadesLoading y propiedadesError— siguiendo el mismo patrón que ya usaba store.computed. Son señales normales, así que las directivas que ya conocías las leen sin necesidad de inventar nada: 

<input data-model="q">

<p data-if="propiedadesLoading">Cargando…</p>
<p data-if="propiedadesError" data-bind="propiedadesError"></p>

<template data-for="propiedades" data-key="id">
  <li><strong data-bind="titulo"></strong> — <span data-bind="precio"></span></li>
</template>

Si hubiera devuelto { data, loading, error } en una sola señal, data-for no la podría leer y habría hecho falta una directiva nueva para cada cosa. Esa decisión es la diferencia entre agregar una API y agregar un lenguaje.

Y cuando falla, no borra la pantalla

Una recarga que falla publica el error en propiedadesError pero conserva el último valor bueno. La lista que el usuario está mirando no desaparece porque se cayó la conexión tres segundos.

Pruébalo aquí

Esto es homly ejecutándose en esta página. Escribe rápido y mira la pestaña de red: hay una sola petición, no una por tecla. El filtro vive en la URL —prueba ?q=cabudare— así un resultado se comparte por enlace. El retardo de 700 ms está simulado y rotulado; sin él la respuesta es instantánea y no se alcanzaría a ver el estado de carga.

Lo demás

Rutas con parámetros

router.add('/blog/:slug', 'blog-post', () => import('./blog-post.js'));

El valor le llega al componente como atributo: this.getAttribute('slug'). Sin API nueva que aprender — los Custom Elements ya tienen atributos, y usarlos evitó inventar un store global de ruta con claves dinámicas. Las rutas estáticas le ganan a las dinámicas sin importar el orden de registro, y el elemento se crea con setAttribute, que nunca interpreta HTML: un segmento de URL no puede inyectar marcado.

Filtros en la URL

Homly.bindQuery(store, ['q', 'orden', 'pagina'], this.signal);

Refleja esas claves en el query string, en ambas direcciones. Convierte según el tipo del valor inicial, porque la URL solo contiene texto y sin eso pagina + 1 daba '21'. Va antes del resource: así la primera petición ya usa los filtros de la URL en lugar de pedir dos veces.

Acciones por fila

borrar: async (target, { item }) => {
  await fetch(`/api/propiedades/${item.state.id}`, { method: 'DELETE' });
}

Un data-action dentro de un data-for recibe el store de su fila. Antes había que escribir el id en el marcado y volver a leerlo con closest.

Homly.head, y una aclaración

Actualiza el título y las etiquetas <meta> al navegar. Y el README lo dice sin rodeos: no es una característica de SEO.

Los scrapers sociales —WhatsApp, Twitter, Slack— no ejecutan JavaScript. Un og:image escrito después de hidratar no existe para ellos.

Para que un enlace se previsualice bien, las etiquetas tienen que venir en el HTML que entrega el servidor. Este post lo hace así: el <head> está escrito en el archivo, y homly hidrata una sola isla —el demo de arriba. Si desactivas JavaScript, el texto se lee igual.

Prefetch al pasar el cursor

Pasar el cursor por un data-router-link —o llegar a él con el tabulador— descarga el chunk de esa ruta. Una sola vez por ruta.

Un bug que ya estaba

Al armar la arquitectura de estos tres sitios apareció otro: el router llamaba a preventDefault() sin mirar nada. Consecuencia: ⌘+clic no abría una pestaña nueva en ningún enlace del router. Nunca. Y un enlace a otro dominio fallaba con un SecurityError, porque pushState entre orígenes distintos no existe.

Ahora se hace a un lado con otro origen, con target, con download y con ⌘/Ctrl/Shift/Alt+clic y clic del medio.

Las primeras pruebas

v1.9.0 estrena pruebas. 102 verificaciones con el assert de Node: sin frameworks, sin fixtures, sin CI, sin toolchain. 

npm test

El criterio quedó escrito en la guía de contribución: se prueba lo que falla en silencio —un parser, una condición de carrera, una conversión de tipos— y nada más. Si una verificación necesita más andamiaje que assert, probablemente el diseño se pueda simplificar.
